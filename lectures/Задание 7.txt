Задание 7: управление перемещениями
Описание

Теперь мы знакомы с транзакциями, и можем взглянуть на нашу систему с точки зрения возможных состояний гонок, приводящих к нарушению инвариантов. Мы продолжим расширять функциональность inventory_manager.
mark order processing

На прошлом занятии мы добавили команду mark order processing. Представим себе ситуацию, что два inventory_manager одновременно пытаются выполнить команду для одного заказа. И первый, и второй получили сообщение с диалогом подтверждения. И первый, и второй нажали подтверждение. Таким образом, может получиться так, что второй затрет processed_by первого. Это гонка данных.

Чтоб избежать этого, нужно выполнять чтение и обновление записи в транзакции, причем чтение должно быть выполнено с блокировкой.
Добавление товаров в перемещение

Также сегодня нужно добавить возможность inventory_manager создавать накладные для перевозки товаров между складами. Это многоcтупенчатый процесс состоящий из следующей последовательности шагов

    Выбор склада отправления из доступных маршрутов
    Выбор склада получения из доступных маршрутов
    Выбор товара из доступных в стоке склада отправления с показом количества или выбор завершить процесс
    Выбор нужного количества
    Подтверждение или отмена с переходом к шагу 3 -- возможность повторить процесс

Инварианты, которые приложение должно соблюдать:

    для каждой пары from - to warehouses должна быть единственная накладная со статусом planned
    в каждой накладной должен быть единственный пункт (transfer item) относящийся к кортежу (transfer_id, created_by, product_id, reserve_id)
    в каждом пункте накладной количество товара > 0
    товар не может пропасть: количество товара в накладной = количеству товара, который вычли из стока

Удаление товаров из перемещения

Многоступенчатый процесс удаления товаров из перемещения:

    Выбор из списка трансферов, в котором есть хотя бы одна позиция, добавленная пользователем
    Выбор товара с показом текущего количества в трансфере
    Выбор количества для удаления
    Подтверждение или отмена с переходом к шагу 2 -- возможность повторить процесс

Инварианты: те же, что и при добавлении.
Просмотр перемещений

Как минимум потребуется просмотр всех запланированных перемещений сгруппированных по маршруту между парой складов (from - to). Каждое перемещение это таблица со следующей информацией:

    ID
    товар (id, название)
    имя пользователя, который добавил товар
    количество
    id заказа, если есть

Задачи

    Запустить две сессии для разных inventory_managers. Повторить состояние гонки, описанное выше.
    Исправить mark order processing, чтоб гонку невозможно было воспроизвести.
    Добавить команды add transfer items и remove transfer items для добавления и удаления товаров в/из перемещения
    Добавить команду list transfers planned all, показывающую все перемещения. Вы можете добавить и другие команды, если нужно. Например, list transfers planned my могла бы показывать перемещения и позиции в них, добавленные текущим пользователем.
    Добавить команду start shipping <transfer_id>, которая меняет статус перемещения с planned на shipping.

Инструкции

Цель этого задания -- научиться использовать транзакции и блокировки, чтоб достичь сериализуемости. Обычно в реальных приложениях состояния гонки проявляются на больших нагрузках и трудновоспроизводимы. В случае REPL приложения мы можем моделировать состояния гонки, запуская две параллельных сессии и используя подтверждения перед каждым запросом.

Поэтому при выполнении заданий предлагается думать о том, будут ли соблюдаться инварианты, если каждый запрос будет ожидать подтверждения.

Подумайте, какие запросы требуют явных блокировок на уровне таблиц и строк, а какие postgres разрулит сам на стандартном уровне изоляции транзакций read commited.
